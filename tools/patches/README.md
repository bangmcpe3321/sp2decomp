# Guest-code and runtime patches

The `gen/` tree is generated from the game's own `main`/`sdk` modules. Changes there are kept
as **idempotent scripts** so they can be re-applied after regenerating and removed for a
control run:

```bash
python3 tools/patches/<patch>.py            # apply
python3 tools/patches/<patch>.py --restore  # remove
```

Each script takes `SP2PORT` (default `~/sp2port`) and edits the file in place. Diagnostics
follow the same convention and are removed before any published run.

| `patch-newsend-bgm-handover.py` | `gen/main/code_213.cpp`, `gen/main/code_027.cpp`, `runtime/include/nx/runtime.h`, `runtime/src/hle_audio.cpp` | The Off the Hook news ends with `SceneBgmPlaza::requestNewsEnding` (reserve region 22, 149 frames at 60 Hz) and the pose waits for `isNewsEndingFinished`, i.e. for a *different* BGM id on `+0x350`. The handover that restarts the plaza BGM runs from the xlink audio callbacks: when the reserved region resolves, `xlinkCalc_` waits one elapsed tick (branch at `0x9dfac0`) and then runs `main_009DF0B4` (`exitState_`) + `main_009DF154` (`onEnterProgress_` → `searchAndPlayBgm_("BGM_SpeakerMain")`, new handle into `+0x350`/`+0x358`) and sets `+0x3f0 = 2`. The stubbed stream player never delivers those callbacks, so the pose hung in mode 1 forever. The patch must not call the handover from the plaza's `xlinkCalc_` itself: that function is only reached through `Cmn::SceneBgm::xlinkCalc` → the xlink conductor at `+0x360`, which stays null until a BGM handle exists (`BgmConductor::xlinkCalc` bails on an empty list), so calling it there re-enters the whole BGM actor from inside its own calc and crashes. Instead: `requestNewsEnding` arms the delay (`nx::hle_audio_news_bgm_arm`), the plaza's `xlinkCalc_` only advances it per frame (`nx::hle_audio_news_bgm_elapsed`), `Cmn::BgmConductor::xlinkCalc` runs the three steps once when it has elapsed (`nx::hle_audio_news_bgm_owner` + `_take`, then the hook retires), and `isNewsEndingFinished` answers "finished" while the handover is pending (`nx::hle_audio_news_bgm_pending`). The pending test is *any* non-zero phase (1 = armed, 2 = elapsed and being taken, 3 = taken): the predicate itself only turns true when `+0x350` holds another BGM id, and by then `searchAndPlayBgm_` has rewritten `+0x350`, so answering it from the real field leaves the pose clock stopped while the handover waits for `isNewsEndingFinished`. `+0x410` is *not* cleared — the predicate needs it. The hooks go inert as soon as the audio layer reports real BGM play events (`hle_audio_note_bgm_play_event`), so on a working audio path the game's own handover runs. Earlier revisions are superseded: one cleared `+0x410` after 149 frames (the predicate returns 0 by definition then), another cleared bit 1 of the 16-bit `+0x3f0` field, which silently turned BGM state 3 into 2 without ever running `onEnterProgress_`. |

`tools/rework/find-dropped-tailcalls.py` is the scan that proved the tail-call case is unique
(final instruction `b <other function>` with no call emitted). Run it against any regenerated
tree before trusting indirect-call crashes.
