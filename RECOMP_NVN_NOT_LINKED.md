# NVN is NOT linked into Splatoon 2 — and Ryujinx's layer is the wrong layer

A decisive architectural check, run before committing to any graphics work. **It rules out one plan and makes
the cheap plan the only plan.**

---

## 1. Can Ryujinx's NVN→Vulkan be reused? **No.**

| Barrier | Detail |
|---|---|
| **Language** | Ryujinx's GPU stack is **C#/.NET**; this port is **C++**. |
| **Layer** | Ryujinx implements **Maxwell / `nvdrv` ioctls**. This game **never calls them** (see below). |
| **Source** | Your install is compiled `publish\` only. Ryujinx was **DMCA'd in 2024**; the original was MIT, forks are legally murky. |
| **If ported anyway** | A C#→C++ rewrite of a Vulkan backend plus a Maxwell shader compiler — years transferred, not saved. |

**The layer mismatch is the decisive one**, and it was worth checking rather than assuming.

## 2. The measurement

Parsing all **146,622** symbol entries in `main`'s table and checking defined-vs-imported:

```
=== nvn* API symbols ===
  [IMP] nvnBootstrapLoader                                  <- IMPORT
  [IMP] nv::InitializeGraphics
  [IMP] nv::SetGraphicsAllocator
  [IMP] nv::SetGraphicsDevtoolsAllocator
  [DEF] nvnLoadCProcs    offset 0xddd6e4, size 12,712        <- DEFINED in main

=== nvdrv / nvhost / nvmap / nvdisp services ===
  total 0                                                   <- ZERO
```

Raw string presence corroborates it: `nvnBootstrapLoader` appears **once** in `main`; `nvdrv`, `nvhost-ctrl-gpu`,
`/dev/nvhost` and `nvdisp` appear **zero** times.

## 3. What that establishes

**NVN is not in the game.** `nvnBootstrapLoader` is an **import** — the game expects the system to supply NVN and
resolves all 453 entry points by name at runtime.

**And the game never touches the driver layer** — no `nvdrv`, no `nvhost`, no `nvmap` calls anywhere in its
symbol table.

**Therefore**: implementing `nvdrv` ioctls — the thing Ryujinx actually does — would serve a layer this binary
**never calls**. That plan is dead.

## 4. What it opens up instead

**`nvnLoadCProcs` is defined in the game** (`0xddd6e4`, 12,712 bytes). The game fills its own 453 globals by
asking a resolver for each name.

> **So the entire GPU surface is controllable through one hook.**

**And the 453 names, in resolution order, already exist in this repo** — `port/src/nvn_names.cpp`, generated by
`tools/static/gen-nvn-names.mjs`, which refuses to emit unless the count is exactly 453. **That earlier work
becomes directly load-bearing.**

## 5. The plan this produces

| Approach | Cost | Needs Vulkan? | Needs shaders? |
|---|---|---|---|
| Real NVN → Vulkan | months–years | yes | **yes** |
| **453 stubs behind one resolver** | **weeks** | **no** | **no** |

**To boot, you do not need Vulkan. You need `nvnBootstrapLoader` to return 453 stubs.**

1. HLE `nvnBootstrapLoader(name)` → a stub per name
2. Stubs return **success + plausible values** — device handles, memory handles, and **fake fence signalling**
3. `nv::SetGraphicsAllocator` / `nv::InitializeGraphics` already stubbed
4. Expect sead to then want VI/display — the next layer

## 6. What this does NOT establish

- **That stub NVN is sufficient to reach a frame loop.** It is the cheapest candidate, not a proven one.
- **That GPU fences can be faked convincingly.** This is the most likely point of failure.
- **That shaders are avoidable** — for *booting*, plausibly; for *rendering*, certainly not.
- **Anything about VI/display**, which has not been examined at all.
- **The port is not booted.** Nothing is rendered. **This is not a playable game.**

## 7. Standing state for the boot effort

| Layer | State |
|---|---|
| Recompiled + linked | ✅ 140,899 functions, 140 MB |
| `nnMain` reached | ✅ |
| sead heap bootstrap | 🟡 **3 of 5 steps** |
| NVN | ❌ **not started — 453 stubs needed, names already catalogued** |
| VI / display | ❌ not examined |
| Shaders | ❌ out of scope, and **not required to boot** |
